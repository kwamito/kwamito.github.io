## Overview

This is a personal side project — a REST API backend for a personal finance and budgeting mobile application. It's different from my professional work in scope (single user at first, no payment gateways, no government requirements) but the same in standards: clean data models, well-designed API, tested, and properly deployed.

Side projects like this serve a specific purpose for me: they're a space to experiment with API design decisions, try data modeling patterns I'm curious about, and build something end-to-end without the constraints of an existing production system.

## What I Built

**Core features:**
- Account management (bank accounts, mobile money, cash)
- Transaction recording with categories, notes, and attachments
- Budget creation with period-based limits by category
- Multi-currency support with exchange rate handling
- Income and expense tracking with flexible date filtering
- Monthly and yearly summary reports

**API design:**
The API follows REST conventions strictly. Resources are nouns, not verbs. HTTP methods carry semantic meaning. Responses use consistent envelope structures. Errors are structured with machine-readable codes and human-readable messages. Pagination is cursor-based.

## Technical Highlights

**Financial arithmetic:**
I use Python's `Decimal` type (not `float`) for all monetary values throughout the application — models, serializers, and computation. The database stores monetary values as `NUMERIC(19, 4)`. Floating-point rounding errors in financial data are a class of bug that's embarrassing and sometimes harmful.

**Multi-currency:**
Each transaction records both the original currency and amount, and the converted amount in the user's home currency at the time of the transaction. Exchange rates are fetched from a public API and cached. Historical conversions preserve the rate at time of transaction — not recomputed at report time.

**Clean URL structure:**
```
GET    /api/accounts/
POST   /api/accounts/
GET    /api/accounts/{id}/
PUT    /api/accounts/{id}/

GET    /api/transactions/?account=&category=&from=&to=
POST   /api/transactions/
GET    /api/transactions/{id}/

GET    /api/budgets/?period=2024-01
POST   /api/budgets/
```

**Django REST Framework:**
DRF's ViewSets and Routers are good for standard CRUD endpoints. For the report endpoints (monthly summary, category breakdown), I used `APIView` directly — more explicit and better for endpoints that don't map cleanly to a single model.

**Tests:**
The project has meaningful test coverage for API endpoints, serializer validation, and the financial calculation logic. Tests use `pytest-django` with `factory_boy` for model factories. No tests that just check that Django returns 200 on a health endpoint.

## What This Project Taught Me

**API design is hard to get right the first time.** I refactored the transaction and budget data models twice before the relationship between them felt clean. Side projects are the right place to make those discoveries.

**Documentation as a practice.** I wrote the API documentation for this project in OpenAPI format, which forced me to think clearly about each endpoint's behaviour, its possible error states, and what clients actually need. It's a habit I've carried into professional work.

**Small scope, full discipline.** Even on a personal project with no users and no deadlines, I set up Docker, a CI pipeline, and proper database migrations from the start. These aren't extras — they're the baseline.
