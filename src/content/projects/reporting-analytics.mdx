## Overview

The source system was a high-volume transactional platform built on Django and PostgreSQL. As record counts climbed into the hundreds of thousands, the management reporting layer hit a wall: reports that were instant on a small dataset started timing out, and the admin interface would block for minutes while they ran. Bigger hardware would not have fixed it. The fix was to change where and how the aggregation happened.

This project is the reporting subsystem: materialized views, indexes, scheduled refreshes and API endpoints that deliver fast, accurate management reporting without touching the performance of the transactional workload.

## The Challenge

Reporting against a transactional database carries a built-in tension. Transactional workloads are optimised for row-level operations — read one record, write one record. Reporting workloads scan, aggregate and join across large sets of records. Serving both from the same tables with the same indexes is a losing trade-off.

Specifically:

- Summary reports aggregated across date ranges, services, statuses and channels, joining several tables at query time
- Heavy `GROUP BY` and aggregate operations competed with write traffic during business hours
- Monthly summaries returned correct results — in 2 to 5 minutes
- No caching strategy: every admin page load re-ran the full query

## Architecture

### Materialized views as the reporting layer

I built a set of PostgreSQL materialized views that pre-aggregate the most common reporting dimensions: daily totals by service, status and channel; monthly summaries; and cumulative totals with period-over-period comparisons.

Celery refreshes the views on a schedule — nightly for daily summaries, hourly for intraday snapshots. The refresh uses `REFRESH MATERIALIZED VIEW CONCURRENTLY`, so the previous data stays queryable while the new version is built.

### Tiered report data

Not every report needs the same freshness, so I tiered them:

- **Live counts** (records created today so far): a lightweight indexed query on the live table, computed on page load
- **Intraday summaries**: an hourly-refreshed materialized view
- **Historical reports**: a nightly-refreshed materialized view, with the refresh timestamp shown to users so they know exactly how current the data is

### API design for reporting

The reporting API takes the report type, date range and grouping dimensions as query parameters, and the backend maps each request to the right materialized view or live query. Responses are structured JSON with totals, breakdowns and metadata — generated at, data as of, and the source tier.

## Technical Highlights

### REFRESH MATERIALIZED VIEW CONCURRENTLY

A plain `REFRESH MATERIALIZED VIEW` takes an exclusive lock and blocks every read. The `CONCURRENTLY` variant builds the new contents alongside the old and swaps them in — no blocking. It requires a unique index on the view, which I defined on each view's natural key.

### Index design for reporting queries

Materialized views still need the right indexes. I added composite indexes on `(date, service_type)`, `(channel, date)` and `(status, created_at)` to match the most common filter combinations in management reports, and confirmed index usage with `EXPLAIN ANALYZE` before and after.

### Separating report reads from transactional writes

On Cloud SQL I set up a read replica and routed the reporting endpoints to it. Transactional writes go to the primary; report reads go to the replica. That removed read/write contention during peak hours, and the admin interface stopped blocking on reports.

### Django management commands for backfills

Each new materialized view needed historical data. I wrote management commands that backfill in configurable batch sizes, log progress, and resume from a checkpoint if interrupted.

## What I Learned

Database performance work starts with measurement. I spent time with `EXPLAIN ANALYZE`, `pg_stat_statements` and slow-query logs before writing any application code. Knowing where the time actually went — sequential scans, sorts, join strategies — told me exactly what to change.

Materialized views are one of PostgreSQL's most underused features for this kind of problem. A materialized view is a real database object with its own statistics and full query-planner support, which makes it more than a cache.
