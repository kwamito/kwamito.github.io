## Overview

I lead the backend for the GETFund scholarship programme in Ghana, and I've written roughly 98% of its 1,054 commits since May 2024.

The platform covers the whole award lifecycle. On the way in: multi-step applications, document vetting, review, shortlisting, interviews and scoring. After the award: offer feedback, visa and travel booking, yearly programme reconfirmation, tuition and stipend payment tranches to universities, programme completion, return procedures and post-study extension requests.

It is a Django 5 and Django REST Framework codebase of 22 apps and around 88 registered API resources, running on Google Cloud with separate dev, staging and production environments.

## The Challenge

The difficulty is that a scholar's record is touched by many people over many years, and each of them is allowed to do something slightly different.

- **Many roles, one record.** Applicants plus 12 staff roles (reviewer, lead reviewer, scholarship team lead, grant manager, finance, travel coordinator, auditor, administrator, education committee, judge, bank manager and IT) all act on the same scholars at different stages.
- **Ordered approvals.** Reconfirmation, completion and tuition payments each pass through several sign-offs in a fixed order. Skipping a step, or two people advancing the same record at once, must be impossible.
- **Accountability.** Any change to a scholar's status, documents or funding has to be explainable after the fact: who did it, when, and what it was before.
- **Bursty load.** When intake reopens, a large number of applicants arrive at once and create applications in the same few minutes.

## Architecture

### Workflows as explicit state machines

Each long-running process is an explicit state machine rather than a set of loosely related flags:

- **Application:** pending → processing → approved or rejected, with a separate blocked state.
- **Yearly reconfirmation** (each year of study, after travel): team-lead review → finance allocation → audit → admin approval → approved or rejected.
- **Completion:** draft → submitted → team-lead review (with revision loop) → audit review → admin review → approved or declined.
- **Tuition payments:** pending → pending approval → approved or rejected → confirmed, plus an on-hold state. Each tranche's status is derived from its audit, approval, bank confirmation and hold flags rather than stored independently, so it can't drift out of sync with them.

Each transition is checked server-side against the acting user's role and the record's current state.

### Permissions composed per endpoint

Access control is built from small role-based permission classes composed per endpoint, then combined with object ownership checks — an applicant sees only their own records, and a reviewer sees only what's assigned to them. Public endpoints are rate-limited.

### Async work and scheduled jobs

Anything that doesn't need to block a request goes through Google Cloud Tasks — including OTP delivery by email and SMS. Scheduled jobs run on App Engine cron. Authentication is JWT with OTP verification.

### Documents and letters

Uploaded documents live in Google Cloud Storage and are served through signed URLs. A companion Node service (Handlebars + Puppeteer) generates 16 types of official letter — award, visa support, bond, tuition-payment instructions, reconfirmation and more — with QR codes and draft/void watermarks.

### Infrastructure

Infrastructure is defined in Terraform, secrets live in Secret Manager, and Redis handles caching. GitHub Actions runs pre-commit checks and the full pytest suite against PostgreSQL on every change, and Sentry reports errors from each environment. API documentation is generated as Swagger/OpenAPI.

## Technical Highlights

### Concurrency-safe state transitions

Approval steps lock the rows they change with `select_for_update`, so two staff members acting on the same record at the same moment are serialised and the second sees the result of the first. Application ID allocation moved to a PostgreSQL sequence, which keeps application creation correct under burst load when intake reopens.

### Full change history for audit

56 models carry full change history via django-simple-history. Every edit to a scholar's application, status or funding is recorded with who made it and what it replaced, so audit questions are answered from data rather than memory.

### Data protection by default

Sensitive financial fields are encrypted at rest. Records are soft-deleted rather than removed, and public identifiers are UUIDs only — sequential database IDs never leave the API.

### Admin performance audit

I audited the Django admin and removed full-table loads from relation fields, so staff pages stay fast as reference and applicant tables grow.

### Data import and reference data

Management commands import schools, courses and other reference data, so new intakes are configured from source files instead of by hand.

### Tests and migrations

1,085 tests across 57 files (pytest + factory_boy) cover permissions, workflow transitions and edge cases. The schema has evolved through 422 migrations.

## What I Learned

On a system like this, the data model is the product. Getting the states and the allowed transitions right — and enforcing them on the server, with row locks where records are contended — removed whole classes of bugs before they could be written.

The other lesson is that auditability is cheapest when it's structural. Change history, soft deletes and derived statuses cost little to add early and are very hard to retrofit once real decisions depend on the data.
