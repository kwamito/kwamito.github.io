## Overview

This project covers the infrastructure work that made the production backend systems reliable, scalable, and deployable without manual intervention. It's the kind of work that doesn't show up in user-facing features but that every other aspect of the system depends on.

The migration moved all services from manually managed Linux VPS instances to Google Cloud Platform, with a fully automated deployment pipeline, managed database infrastructure, proper secrets handling, and container-based deployments.

## The Problem

The previous infrastructure state was common for small engineering teams moving fast:

- Production running on VPS instances configured manually, with no documentation of the exact setup
- Deployment meant SSH-ing into the server, pulling code, running migrations, and restarting the service — no automated steps, no rollback plan
- Database backups happened manually, on a schedule that required remembering
- API keys and database credentials were stored in `.env` files on the server
- A bad deployment that needed rollback meant SSH-ing back in and reverting manually

This setup worked — until it didn't. A failed deployment during business hours with no automated rollback and a manual recovery process is the kind of event that makes teams nervous about deploying at all.

## What I Built

### Cloud Run for application containers

Each service is packaged as a Docker container and deployed on Google Cloud Run. Cloud Run is a good fit for Django applications because:

- It scales to zero between requests (no idle costs)
- It scales horizontally automatically under load
- Traffic routing between revisions allows gradual rollouts
- Each revision is immutable — "rollback" means routing traffic to a previous revision

### Cloud SQL for managed PostgreSQL

The PostgreSQL database was migrated to Cloud SQL (PostgreSQL edition). Cloud SQL handles automated backups with configurable retention, point-in-time recovery, high availability with automatic failover, and maintenance windows that don't require manual intervention. The Cloud SQL Auth Proxy handles connectivity from Cloud Run without exposed database IPs.

### GCP Secret Manager for all secrets

Every secret — database credentials, third-party API keys, Django `SECRET_KEY` — is stored in Secret Manager. Application containers pull secrets at startup. No secrets in environment variable files. No secrets in source code. Secret access is controlled by IAM service accounts with the minimum required permissions.

### GitHub Actions CI/CD pipeline

```
push to main
  → run tests (pytest)
  → build Docker image
  → push to Artifact Registry
  → deploy to Cloud Run (new revision)
  → run smoke tests against new revision
  → promote revision to 100% traffic
```

If any step fails, the pipeline stops. The previous Cloud Run revision continues serving traffic. No manual intervention needed for routine deployments.

### Cloud Storage for media and document files

All user-uploaded files and generated documents are stored in Cloud Storage buckets with appropriate lifecycle policies. Application code never stores files on the container filesystem — containers are ephemeral and stateless.

## Technical Highlights

### Docker image optimization

Django Docker images can get large and slow to build. I used multi-stage builds to separate the dependency installation step (slow, but cacheable) from the application code copy (fast). Using `.dockerignore` to exclude unnecessary files kept the final image small and builds under 2 minutes.

### Database migration safety

Cloud SQL combined with the CI/CD pipeline introduced a discipline around migrations: migrations run as a separate step before the new container revision handles traffic. The old container revision continues running during migration. This means migrations must be backwards-compatible — additive, not destructive.

### IAM least-privilege

Each Cloud Run service has its own service account with only the permissions it needs. The API service can read secrets, access Cloud SQL, and write to its specific storage bucket. It cannot access secrets belonging to other services, cannot access other databases, and cannot list all buckets. IAM review is part of every new service setup.

### Health checks

Each Django service exposes a `/healthz/` endpoint that checks database connectivity and returns a structured JSON response. Cloud Run uses this for startup and liveness probing — a container that can't reach the database won't receive traffic.

## What I Learned

Infrastructure work is mostly about removing yourself from the critical path. The goal isn't to do deployments faster — it's to make deployments so reliable and automated that they're not events you worry about.

The most valuable thing this migration produced wasn't faster deployments — it was the confidence that came from knowing exactly what was running, exactly how it was configured, and exactly what would happen when a deployment was triggered.
